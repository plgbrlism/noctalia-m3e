We provide an experimental notification-based (`Type=notify`) systemd user service for Vespertine. If your compositor is started as a systemd user service, then instead of launching Vespertine from your compositor configuration, you can enable this service so that systemd automatically starts Vespertine after the compositor.

Benefits:

1. The Vespertine service blocks subsequent services having `After=graphical-session.target` (e.g. XDG autostart apps) from starting, until Vespertine finishes starting up. This cleanly fixes the race condition, where an autostart app might try to register with the systray before Vespertine starts listening on the systray D-Bus interface, thus failing to show its systray icon.
2. Vespertine runs in its own cgroup, isolating its resource usage from other processes. And you can set resource limits for it independently in the service file.

(**Note:** With Nix, the ordering guarantee of point 1 above requires `programs.vespertine.systemd.target` to be the compositor's target, e.g. `umbriel-session.target`.)

## Supported Compositors

The following compositors are supported in their own Wayland sessions:

- KDE Plasma
- Labwc
- Mango
- Niri
- Umbriel

The following compositors are only supported in [uwsm](https://github.com/Vladimir-csp/uwsm) sessions (because they don't run as systemd user services in their own sessions, nor do they pull in their own systemd session target):

- Hyprland
- Sway / Scroll

## Installation

1. Copy `vespertine.service` from `/usr/share/vespertine/assets` to `$HOME/.config/systemd/user/`. (Depending on your installation method, the source dir could be `/usr/local/share/vespertine/assets` or `$HOME/.local/share/vespertine/assets` instead.)
2. Edit the copied service file. Uncomment (remove the leading `#`) the `WantedBy=` line for the compositor you want to enable Vespertine for.
3. Reload the systemd user daemon: `systemctl --user daemon-reload`
4. Enable the Vespertine service: `systemctl --user enable vespertine.service`

To uninstall, run `systemctl --user disable vespertine.service` (or delete `$HOME/.config/systemd/user/*.wants/vespertine.service`).

It's also recommended to enable the "Launch Apps as systemd Services" option in "Shell" settings. This puts apps launched from Vespertine in their own transient systemd services, so they won't be killed when you restart Vespertine (e.g., after upgrading it).

### Labwc

For Labwc (when not started via `uwsm`), you also need to add the following line to `$HOME/.config/labwc/autostart`:

```sh
systemctl --user --no-block start labwc-session.target
```

And the following line to `$HOME/.config/labwc/shutdown`:

```sh
systemctl --user stop graphical-session.target
```

## Implementation Details

We need to ensure that:

1. Vespertine starts after the compositor is ready.
2. Vespertine is ready before XDG autostart apps are launched. (This ensures that autostart apps can register with the systray successfully.)

### Start Vespertine after the compositor is ready

#### Compositors that run as systemd user services: KDE Plasma, Niri, Umbriel

These compositors run in their own systemd user services, and only mark the unit active when they are ready. So `vespertine.service` has `WantedBy=` for their services or session targets, and `After=` for their services.

#### Compositors that do not run as systemd user services: Labwc, Mango

These compositors do not run as systemd user services, but they start a session target only after they are ready. So `vespertine.service` has `WantedBy=` for their session targets. We don't need `After=` for them, because when the session target starts, they are already ready.

#### Compositors managed by `uwsm`: Hyprland, Sway / Scroll

For these compositors, `uwsm` handles starting the compositor and marking it ready. `vespertine.service` has `WantedBy=` for `wayland-session@<compositor>.desktop.target`, and `After=` for `wayland-session-waitenv.service`, which waits until the necessary environment variables (`WAYLAND_DISPLAY` and others) are set (thus the compositor is ready) before Vespertine starts.

(**Note:** `WantedBy=wayland-session@<compositor>.desktop.target` only works if your `uwsm start` command runs a desktop file (e.g., `uwsm start -e -D Hyprland hyprland.desktop`). If it runs a compositor executable directly (e.g., `uwsm start -e -D Hyprland hyprland`), then you may need `WantedBy=wayland-session@<compositor>.target` instead. To find the correct target name, run `systemctl --user list-units | grep wayland-session` in your uwsm session.)

### Ensure Vespertine is ready before XDG autostart apps are launched

`vespertine.service` has `Before=graphical-session.target`, while XDG autostart units have `After=graphical-session.target`. So Vespertine will be ready before any XDG autostart apps launch.

## Troubleshooting

If some apps launched from Vespertine don't use the cursor theme and size in your compositor config, but when launched via a compositor keybinding they work correctly, it's usually because the compositor doesn't export the `XCURSOR_THEME` and `XCURSOR_SIZE` environment variables to the systemd user manager, so apps spawned directly for the compositor inherit them, but Vespertine itself and apps launched from Vespertine do not. To fix this, you can enable "Launch Apps as systemd Services", and add the following to the autostart section in your compositor's configuration file:

```sh
systemctl --user import-environment XCURSOR_THEME XCURSOR_SIZE
```
